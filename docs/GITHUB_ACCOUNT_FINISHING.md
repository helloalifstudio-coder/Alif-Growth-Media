## 5. Make every public project credible

- Open with **what problem the software addresses**, who it is for, and current project status.
- Add **3–5 real screenshots** where useful. Do not use fabricated dashboards or unrelated stock images and call them product screenshots.
- Include a **demo link**, tech stack, setup instructions, known limitations, and license when appropriate.
- Distinguish **customer deployments**, **concepts**, **research**, and **forked/adapted work**. Preserve upstream licensing and attribution.
- Never claim zero bugs, guaranteed uptime, security certifications, client growth percentages, or customer testimonials without evidence.
- Add a case study only after collecting an approved problem statement, screenshots and results.
- Keep API keys, database passwords, personal data, contracts, and client credentials out of public repositories.

### Public file privacy review

The public agency repository contains an `Agm/` folder with business-related images and a **registration-certificate PDF**. Review whether every document is intended to be public. If a file contains sensitive identifiers or signatures, removing it from the latest commit **does not remove it from historical Git commits**; follow GitHub's guidance for sensitive-data remediation and rotate or invalidate exposed credentials where relevant. Do not share private customer documents through the portfolio.
